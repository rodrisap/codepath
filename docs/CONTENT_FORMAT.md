# Content format

Lessons are **data**, not code. To add a lesson you write two small files and run one command. You never touch the React app.

```
content/
  python/
    track.ts                      ← module + lesson order and titles
    loops/                        ← one folder per module (the module id)
      for-range/                  ← one folder per lesson (the lesson id)
        lesson.md                 ← the prose (Markdown)
        lesson.ts                 ← everything structured: example, exercises, tests, quiz
        generated.json            ← created by `npm run content` (don't edit)
```

## 1. Register the lesson in `track.ts`

```ts
{
  id: "loops",
  title: "6. Loops",
  summary: "Repeating work with for, while and range.",
  lessons: [
    { id: "for-range", title: "for loops & range()" },
    { id: "project-occupancy", title: "Project: weekly occupancy report", kind: "project" },
  ],
},
```

`kind` is `"lesson"` (default), `"project"` or `"capstone"`. A lesson listed here without a folder appears in the sidebar as *coming soon*.

## 2. `lesson.md`: the prose

Sections start with `## `. Which ones are required depends on the kind:

| Kind | Required | Optional |
|---|---|---|
| lesson | `## Concept`, `## Common mistakes` | `## How it runs` (shown under the example's output) |
| project / capstone | `## Brief` | |

Guidelines:

- **Concept**: at most ~150 words, plain language, **one real-world analogy**. The checker warns above 170 words.
- **Common mistakes**: 2–3 typical errors, each with the code, the *real* error message in a ```` ```text ```` block, and how to read it.
- Code blocks with ```` ```python ```` or ```` ```sql ```` are syntax-highlighted.

## 3. `lesson.ts`: the structured parts

```ts
import { defineLesson } from "../../../../src/content/types";

export default defineLesson({
  goal: "One sentence: what you can do after this lesson.",

  // Worked example. The step-by-step trace is GENERATED by running this code,
  // so it is always correct. Never write traces by hand.
  example: {
    intro: "Optional Markdown above the code.",
    code: `total = 0
for rate in [450, 500]:
    total += rate
print(total)
`,
    stdin: ["3"],          // optional: lines typed when the code calls input()
    files: { "bookings.csv": "..." },   // optional: files the code can open()
    expectError: "NameError",           // optional: the example is meant to crash
  },

  tryIt: { prompt: "What to change and predict.", code: "optional different starting code" },

  exercises: [
    {
      id: "booking-total",                     // unique within the lesson; used to save progress
      title: "Total for a booking",
      prompt: "Markdown task description.",
      starter: "def booking_total(nights, rate):\n    ...\n",
      stdin: ["3", "450"],                     // optional default input for all tests
      tests: [ /* see below */ ],
      hints: ["a nudge", "a stronger hint", "almost the answer"],   // exactly 3
      solution: { code: "...", explanation: "Markdown: why this works." },
      wrongAnswers: ["plausible wrong code that MUST fail"],        // at least 1
    },
  ],

  quiz: [ /* 2–3 questions, see below */ ],
});
```

**Watch out in TypeScript template literals** (the `` `...` `` strings): `\n` becomes a real newline, and `${` starts a placeholder. Python code rarely needs either. If it does, write `\\n`.

### Test kinds (Python)

Every test can have a `label` (shown in the results), a `hint` (added to the failure message) and its own `stdin`.

| kind | Checks | Example |
|---|---|---|
| `output` | the whole printed output, line by line (prompts and typed input included) | `{ kind: "output", expect: "Total: 150" }` |
| `contains` | the output contains each piece | `{ kind: "contains", expect: ["150", "MXN"] }` |
| `var` | a variable's value after running | `{ kind: "var", variable: "total", expect: 150 }` |
| `call` | calls an expression after running | `{ kind: "call", call: "booking_total(3, 50)", expect: 150, hint: "Check if you multiplied by nights." }` |
| `raises` | the program (or `call`) raises this exception | `{ kind: "raises", call: "parse_nights('x')", expect: "ValueError" }` |
| `py` | custom Python: has `ns` (variables), `output`, `lines`, `fail(msg)` | `{ kind: "py", label: "rate is a float", check: "if type(ns['rate']) is not float: fail('...')" }` |
| `source` | a regex on the code (comments stripped unless `raw: true`); `negate: true` = must NOT match | `{ kind: "source", label: "uses an f-string", pattern: "\\bf[\"']", message: "Use an f-string." }` |

Numbers are compared with a tiny tolerance, so `0.1 + 0.2` equals `0.3`. Feedback is generated automatically, e.g.:

> `booking_total(3, 50)` should return 150, but it returned 53. Check if you multiplied by nights.

Common mix-ups get an extra sentence automatically: a returned `None` ("no `return`?") and text vs number.

### Quiz questions

```ts
{
  id: "predict-loop",              // unique within the lesson; used by the Review page
  kind: "predict",                 // "predict" | "bug" | "choice"
  question: "What does this print?",
  code: `print(7 // 2)`,
  options: ["3.5", "3", "4"],
  answer: 1,                       // index into options
  explanation: "Markdown shown after answering.",
}
```

For `predict` questions the checker **runs the code** and fails if the marked option isn't the real output (use the exception name, e.g. `"ValueError"`, when the code crashes).

## 4. Run the checker

```bash
npm run content                   # verify everything and (re)generate traces
npm run content -- --only=loops   # just one module or lesson
npm run content -- --verbose      # also show the feedback each wrong answer gets
npm run verify                    # CI mode: also fails if a generated.json is stale
```

It fails if:

- any part is missing, or there aren't exactly 3 hints
- the example crashes (unless `expectError`)
- a **solution fails** any test
- a **wrong answer passes** all tests (the tests are too weak)
- a predict question's answer isn't the real output

## SQL lessons (Phase 3)

SQL exercises use the same file layout. Instead of Python tests, an exercise declares a dataset and an expected query. The checker compares result sets (columns, row count, values, order). The exact fields are documented here when the SQL track is built.
